## 发布流程

参考 [knowledge 的 Actions](https://github.com/Flobby949/knowledge/blob/main/.github/workflows/deploy.yml)，推送新的 `vMAJOR.MINOR.PATCH` 标签发布；标签须指向 `main` 上的提交。

1. GitHub Actions 启动临时 MySQL/Redis，执行非缓存 Go race 集成测试和 vet。
2. 构建 `linux/amd64` 镜像到私有 GHCR 包，以版本和提交 SHA 标记。
3. 通过专用 SSH 密钥调用服务器固定部署脚本，实际部署使用不可变镜像 digest。
4. 首次部署初始化独立数据库；后续部署先停止 API，同时暂停业务与微信投递，保存数据库和图片备份，再启动新 API、执行迁移并检查健康状态。

启动或重建不删除持久卷。不要执行生产 `docker compose down -v`。启动迁移包含 MySQL DDL，失败后须检查已执行语句；脚本不会自动回滚数据库或盲目重试迁移。

## 服务器首次准备

服务器现状：CentOS 7、x86_64、Docker 26.1.4、Compose 2.21.0，内存约 1.7 GiB；2026-10-22 检查时可用约 670 MiB，无 swap，已有其他业务和 MySQL 容器。Compose 为新 MySQL、Redis、API 分别设置 384/64/256 MiB 上限，首次启动后仍需检查真实内存、OOM 和健康情况。

在本地准备不进入 Git 的一次性目录，包含以下文件，然后通过当前已认证的管理连接上传：

- `compose.yaml`、`deploy.sh`、`bootstrap.sh`、`nginx-location.conf`，取自 `deploy/`。
- `.env`，按 `deploy/.env.example` 填写；三个独立随机十六进制密码，微信凭据仅放在此文件。
- `notification-mappings.json`，取自已验真的本地 `backend/.env.notification-mappings.json`，包含 30 项业务提醒。
- `deploy-key.pub`，本项目专用 SSH 公钥。私钥保留给本仓库 Actions，不上传到服务器。

确认文件后在该目录执行 `bash bootstrap.sh`。脚本创建 `/opt/couple-mini`，增加 Nginx 路径、验证并 reload Nginx，为专用公钥设置 forced command。该密钥只能调用本项目部署脚本，不允许交互 shell、PTY 或端口转发。现有 SSH 登录方式保持可用。

本机 Nginx 由已有进程运行，使用 `nginx -s reload`。部署入口和 Compose 文件由管理员首次安装并持有；后续修改这些文件时需通过管理连接更新服务器副本，Actions 的受限密钥仅更新本项目镜像版本。

GitHub 私有仓库 `Flobby949/couple-mini` 的 Actions Secrets：

| Secret | 内容 |
| --- | --- |
| `DEPLOY_HOST` | 目标服务器 IP |
| `DEPLOY_SSH_KEY` | 本项目专用 Ed25519 私钥 |
| `DEPLOY_KNOWN_HOSTS` | 从当前已认证连接核对指纹后的服务器 Ed25519 known_hosts 行 |

GHCR 使用作业自身的 `GITHUB_TOKEN`，不需要另建长期 registry token。服务器使用临时 Docker 登录目录，部署退出后删除该目录，不覆盖其他项目的 Docker 凭据。应用配置与私钥不得提交到仓库或构建上下文。

## 运维与恢复边界

### 数据导出与图片备份

新增独立脚本 [backup-data.sh](../deploy/backup-data.sh)。将它放在服务器 `/opt/couple-mini/`，与 `compose.yaml`、`.env`、`.current-image` 同目录，再执行：

```sh
# 仅检查目标和预览范围，不导出、不重启 API
bash /opt/couple-mini/backup-data.sh

# 导出数据库和图片，保留现有业务数据
bash /opt/couple-mini/backup-data.sh --backup
```

2026-10-22 14:53（北京时间），已通过 Netcatty 管理连接更新 `/opt/couple-mini/backup-data.sh`，移除镜像版本引用，权限为 `700 root:root`。服务器 SHA-256 与本地一致（`ffdac1b9534f5bc36753bed87ea0977e1639f3188a295e0676662aabbd13dff9`），`bash -n` 与 `--dry-run` 通过，预览识别 18 个已登记图片。仅更新及预览，未执行实际导出；检查时 API 为 running/healthy，本次操作未停止或启动 API。

MySQL 需处于运行状态，API 容器需存在。脚本与部署/重置共用 `.deploy.lock`；实际导出时短暂停止原本运行的 API，暂停请求写入、后台结算和通知任务，让 SQL 与图片形成同一个恢复点。成功或失败都会尝试启动原容器并等待健康，不重建容器、不切换镜像；API 原本已停止则保持停止。导出期间不要另行手工写入数据库或图片目录。

输出是单个 `backups/export-<UTC时间>-<进程号>.tar.gz`，包含：

- `database.sql`：MySQL 表结构、全部数据及 `schema_migrations`，包含头像和商品封面的文件关联。
- `media.tar.gz`：`/app/uploads/` 下的全部实际图片文件，包括头像、封面、旧订单快照引用的图片及未引用文件；保留原文件 ID 和目录。
- `SHA256SUMS`：上述两个数据文件的 SHA-256 校验和。

纯 SQL 不能同时打包图片，因此由脚本生成可直接导入的 SQL，并和图片放在同一个压缩包中。图片以文件 ID 保存，没有扩展名，不能在恢复时改名；备份的是服务器实际保存的文件，当前上传流程会重编码，不是手机上传前未经处理的原图。Redis 登录会话及服务器配置/凭据不包含在压缩包中，导出不会清理它们。

备份包不包含 Docker 镜像或镜像版本引用。脚本读取 `.current-image` 只是为了使用现有 Compose 配置，不将其打包。

导出还会核对每个 `media_files.id` 是否在图片包中，发现缺失图片即失败。未完成文件保留在 `.partial` 目录，不能当作成功备份。最终压缩包只在 SQL、图片及校验检查通过后生成；若随后 API 恢复失败，脚本仍返回失败并保留已经完成的压缩包。权限默认仅允许执行用户读写，仓库忽略 `deploy/backups/`。

复制压缩包到独立备份位置后，可先在独立目录解包和校验：

```sh
mkdir restore-check
tar -xzf /path/to/export-YYYYMMDDTHHMMSSZ-PID.tar.gz -C restore-check
(cd restore-check && sha256sum --check SHA256SUMS)
tar -tzf restore-check/media.tar.gz
```

恢复时 SQL 和图片须使用同一份压缩包，先在独立数据库/图片目录演练，再按下文恢复边界处理生产数据和已发通知，必要时重新登录。以上导出命令不执行恢复或清空。

隔离验证使用 `bash deploy/tests/backup-data.sh`，需要 Docker、Compose、已缓存的 MySQL/Redis 镜像及 `couple-mini-backend:deploy-check`。测试覆盖默认预览、互斥锁、完整 SQL/图片恢复、用户头像循环外键、图片字节及校验和、备份失败恢复 API、缺失引用图片、原本停止的 API、恢复失败时保留压缩包；只创建和清理独立测试项目。

### 测试数据重置

服务器脚本 [reset-test-data.sh](../deploy/reset-test-data.sh) 已安装在 `/opt/couple-mini/reset-test-data.sh`，权限为 `700 root:root`，已通过校验及预览。脚本使用同目录的 Compose 配置、`.env` 和 `.current-image`，与部署共用锁；默认只预览各业务表行数，不清空数据。

```sh
# 预览范围
bash /opt/couple-mini/reset-test-data.sh

# 明确执行：停止 API、备份后重置，最后恢复并检查 API
bash /opt/couple-mini/reset-test-data.sh --confirm-reset
```

重置覆盖所有账号及头像昵称、情侣绑定、共同规则、积分、商品、购物车、订单、任务、消息与订阅投递记录，并清除 Redis `couple:session:*` 会话和上传目录中的全部图片。保留表结构、外键与 `schema_migrations`，序列计数器继续递增；双方重新登录、绑定和确认规则后重新开始。手机遇到过期会话时会重新登录；无需重新上传小程序。

执行前暂停 API 及其后台任务，将完整 SQL、上传图片和当前镜像引用保存到 `backups/reset-<UTC时间>-<进程号>/`。备份失败不清空业务数据，并恢复原先运行的 API；清空已开始后若中断，则保留 API 停止状态，打印备份路径，供核查或恢复。重置业务表采用事务删除，外键检查仅在该连接中临时关闭，以处理用户头像与媒体归属的循环引用。恢复方式沿用下文数据库和图片成套恢复原则，登录会话需要重新建立。

隔离验证使用 `bash deploy/tests/reset-test-data.sh`，需要 Docker、Compose，以及已有的 `couple-mini-backend:deploy-check` 镜像（可用 `docker build -t couple-mini-backend:deploy-check backend` 构建）。测试建立独立项目、数据库和图片卷，验证预览、并发锁、备份失败、清空、备份恢复及中途失败后 API 停止，退出时只清理该测试项目。

服务器管理终端中，先加载上次通过健康检查的镜像引用：

```sh
cd /opt/couple-mini
export BACKEND_IMAGE="$(cat .current-image)"
docker compose --env-file .env -f compose.yaml ps
docker compose --env-file .env -f compose.yaml logs --tail=100 api
```

后续发布的备份保存在 `backups/<UTC时间>/`，含 `database.sql`、`media.tar.gz` 和当时的镜像引用。数据库与图片必须成套保留；只在服务器保存备份不足以应对磁盘丢失，还需复制到独立位置并设置保留策略。

恢复时先停止 API，确认迁移版本和图片引用，并核对备份后实际发出的微信消息，保留这些投递的已成功/未知状态，避免恢复旧数据库后重复通知。先在独立临时数据库、图片卷演练恢复，验证余额、流水、图片和版本，再安排生产恢复。Redis 中的登录会话未纳入 SQL/图片备份，必要时重新登录。

部署失败时 `.current-image` 保留上个健康版本。检查迁移是否完成并确认版本兼容后再选择旧镜像启动；不要用容器镜像回退替代数据库恢复。
