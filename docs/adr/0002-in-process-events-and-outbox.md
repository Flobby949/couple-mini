# 业务事务保存领域事件，提交后处理通知

订单、任务、签到等业务需要触发消息，积分、库存和日额度必须与业务状态一起确定。整体架构复核后的建议是：主业务通过同步模块调用完成必要结算，并在同一事务保存领域事件及冻结的通知上下文到事件 Outbox；事务提交后由进程内事件分发器调用消息订阅者。

事件总线开启独立消费事务，消息处理器在其中生成站内消息及渠道投递记录，再由事件总线写入消费收据并一起提交；后台调度随后驱动微信发送。事件消费按事件和订阅者记录进度，逻辑通知按事件、接收人和模板去重；重复消费不重复生成通知。微信发送成功、明确失败和结果未知分别处理，内部幂等不代表平台端严格只投递一次。

原先建议在主事务中运行消息处理器，会使模板故障阻塞下单或任务提交，因此将通知生成移到提交后。代价是增加持久化消费进度，通知会晚于业务结果出现；任务奖励仍在原事务内结算，消费者只使用实际到账、业务名称及已解析默认值的渠道偏好快照，防止跨日或设置变更改写原结果。

事件 Outbox 及订阅进度归事件总线，站内消息和渠道投递记录归消息模块。启动装配注册处理器与后台作业，基础模块通过注入的回调执行工作，不导入具体业务模块。详细流程见 [开发规格第 8.5 节](../PRD.md#85-领域事件总线与事务性-outbox)；此方案已在第四轮实现，通知与消费收据同事务提交，微信网络发送使用独立作业；真实平台模板及投递仍需账号接入核验。
